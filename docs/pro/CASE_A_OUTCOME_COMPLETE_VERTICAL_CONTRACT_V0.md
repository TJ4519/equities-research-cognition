Status: **accepted for bounded implementation** after independent hostile review result `99ad9412f059239c0604497b3de868b6c348370a` with verdict `ACCEPT_WITH_EXACT_NARROWING`.

This contract adopts every severity-one and severity-two closure in `docs/pro/evidence/HOSTILE_VERTICAL_REVIEW_RECEIPT.md`. It does not establish product readiness, analyst usefulness, Excel compatibility, professional correctness, permission to rely, harness improvement, deployment, or client readiness.

## 1. Product purpose

The first implementation must prove that one recognisable analyst job can move through exact meaning, bounded work, deterministic containment, attributed repair, native-artifact consequence, restart, and a protected correction seed without exposing the harness as the product.

The product centre remains a continuing company-research environment with specialised workspaces. This contract implements one specialised model-change workspace. Excel is the first artifact-adapter question, not the product ontology or permanent shell.

## 2. Exact completion unit

The accepted implementation unit is one Case A episode:

```text
authenticated owner resumes one synthetic Micron ResearchJob
-> one immutable ModelChangeEpisode binds the exact starting workbook and captured sources
-> host inspects one stable numeric target and two declared dependents
-> model proposes bounded economic meaning
-> human confirms or amends that exact meaning
-> human separately authorises the reported-value method and target-specific source policy
-> host compiles one typed, digest-bound work packet with search closed
-> one real NTM/Codex worker returns the controlled 8-K proposal
-> host returns BLOCK_WRONG_DOCUMENT_CLASS before any candidate exists
-> user chooses “Create a candidate using the filed annual report”
-> attributed Amendment creates a replacement proposal bound to the captured 10-K
-> deterministic PASS is required before a child workbook exists
-> bounded adapter patches and calculates the child
-> product shows exact source, before/after target, two consequences, engine identity and formula-error state
-> user records SIMULATE_NAMED_USE, REJECT or REWORK
-> restart reconstructs the same current state and immutable history
-> host emits one exact CorrectionRecord seed
```

The implementation is incomplete if any of those joins is replaced by a document, mock-up, raw JSON, manually attached result, hard-coded downstream values, direct database fixture presented as runtime work, or separate capability slices that never complete the professional path.

## 3. Visible ordinary-language journey

## 5. Minimum additive canonical population

Only the following new canonical records are authorised for the first implementation:

1. `ResearchJob`: authenticated owner, company reference, optional mandate reference, creation metadata.
2. `ModelChangeEpisode`: job, one-to-one existing `ResearchCampaign`, immutable objective, named synthetic use, cutoff, starting artifact.
3. `ArtifactManifestVersion`: host-inspected target, allowed operation, two-dependency closure, adapter/profile version, digest, support/refusal facts.
4. `ConceptualObjectVersion`: immutable parent, optional manifest binding, economic meaning, method/source-policy representation, binding status, claim ceiling.
5. `ObjectDisposition`: exact object version, actor, and typed `CONFIRM_MEANING`, `AMEND_MEANING`, or `AUTHORIZE_METHOD` act.
6. `SourceDocumentVersion`: overlay of exact `ArtifactVersion` bytes with host capture/access metadata and document identity.
7. `SourceAssertion`: exact document version, locator, value, units/dimensions, target-compatibility facts, digest.
8. `ModelChangeProposal`: immutable ancestry, proposer kind, episode, object, artifact, assertion, operation, protocol version, claim ceiling.
9. `AdmissibilityDecision`: proposal, validator version, `PASS`, `BLOCK`, `UNSUPPORTED`, or `JUDGMENT_REQUIRED`, reason codes, closure digest.
10. `CalculationReceipt`: candidate, adapter/engine/profile versions, input/output digests, operation receipt, two declared outputs, warnings, formula errors.
11. `Amendment`: actor, exact ancestor, bounded action, rationale, replacement reference.
12. `InvalidationEvent`: amendment, invalidated descendant, reason, closure digest.
13. `ArtifactDisposition`: exact candidate and named use; only `SIMULATE_NAMED_USE`, `REJECT`, or `REWORK`.
14. `CorrectionRecord`: exact evaluation seed; no failure attribution, intervention, evaluation, promotion, or release record.

Extend existing `ArtifactVersion` additively with nullable parentage and candidate-from-pass linkage. Existing rows remain valid.

The following remain projections, versioned JSON fields, or deferred concepts in V0: explicit tenant and membership, separate objective version, standalone artifact binding, standalone dependency closure, standalone method/source-policy tables, entitlement receipt, work plan, cognition package, professional exception, separate candidate-artifact model, and failure attribution.

The following are entirely outside this implementation: evaluation runner, intervention candidate, promotion decision, harness release, planner stage, adversarial-review stage, synthesis stage, judgment stage, dashboard, provenance console, institutional-memory browser, generic activity feed, and multi-agent monitor.

```text

  -> SourceDocumentVersion

  -> SourceAssertion

WorkCompiler.compile(episode, current_object, current_authority, manifest,
                     captured_assertions, protocol_version)
  -> immutable WorkOrder packet

ProposalParser.parse(worker_output, exact_packet)
  -> ModelChangeProposal | bounded refusal

AdmissibilityGate.evaluate(proposal, current_closure)
  -> AdmissibilityDecision(PASS | BLOCK | UNSUPPORTED | JUDGMENT_REQUIRED)

CandidateService.create(pass_decision, exact_parent, adapter_profile)
  -> child ArtifactVersion + operation receipt + CalculationReceipt

DispositionService.record(actor, candidate, named_use,
                          SIMULATE_NAMED_USE | REJECT | REWORK)
  -> ArtifactDisposition

InvalidationService.amend(actor, exact_ancestor, bounded_change)
  -> Amendment + replacement + InvalidationEvent[]
```

Every interface accepts canonical identifiers and digests, returns canonical records, and refuses stale or cross-scope inputs. Views render projections and submit bounded commands. Views do not inspect workbook truth, compile authority, spawn processes, decide admissibility, infer current ancestry, or issue source identity.

## 9. Deterministic admission and candidate-after-pass law

The gate compares the exact proposal closure against the exact current episode, object, manifest, source assertion, source policy, cutoff, operation, artifact, units, and allowed profile.

Required reason codes include at minimum:

- `BLOCK_WRONG_DOCUMENT_CLASS`;
- `BLOCK_STALE_CLOSURE`;
- `BLOCK_UNKNOWN_HOST_IDENTITY`;
- `BLOCK_CROSS_EPISODE_REFERENCE`;
- `BLOCK_WRONG_OBJECT`;
- `UNSUPPORTED_PROFILE`;
- `UNSUPPORTED_STRUCTURAL_OPERATION`;
- `JUDGMENT_REQUIRED`; and
- `PASS`.

No candidate may exist unless one current `PASS` decision references the same proposal, episode, object version, source assertion, parent artifact, operation, manifest, and closure digest. Enforce this in services and at the database boundary where possible.

The controlled first 8-K proposal is retained as immutable blocked evidence. The attributed action creates a new proposal; it never rewrites the failed proposal.

## 10. Bounded artifact adapter

The only accepted adapter profile is:

- direct OOXML inspection and patching of one workbook-defined numeric input;
- exactly two declared arithmetic dependents;
- no macros, external links, data tables, volatile functions, circular calculations, protected structure, or structural row/formula insertion;
- pinned LibreOfficeDev calculation proxy with exact build recorded; and
- safe `UNSUPPORTED_PROFILE` or `UNSUPPORTED_STRUCTURAL_OPERATION` refusal outside the envelope.

Stable boundary:

```text
inspect(workbook_bytes, profile) -> ArtifactManifestVersion
apply(parent_bytes, admitted_operations, expected_manifest_digest)
  -> candidate_bytes + operation_receipt
calculate(candidate_bytes, profile) -> CalculationReceipt
compare(parent_bytes, candidate_bytes, dependency_closure)
  -> declared_consequences
```

Only the audited host-process boundary may spawn LibreOffice. It must use an exact binary allowlist, argument grammar, timeout, isolated temporary profile, controlled environment, and `shell=False`. Spawning from a view, arbitrary service, spike script, or new general-purpose helper is prohibited.

The original remains byte-for-byte unchanged. Cached or dependent values may not be fabricated manually.

## 11. Restart, invalidation, and rollback

Restart is a projection over immutable records, not a live NTM session. The page must reconstruct the current object, authority, proposal, decision, candidate, receipt, disposition, correction, and immutable history without Langfuse, terminal state, or in-memory state.

Any material amendment to object meaning, method/source policy, source assertion, starting artifact, manifest, operation, or assumption creates a new version and exact `InvalidationEvent` records. It invalidates named downstream proposal, decision, candidate, calculation receipt, and synthetic disposition. A stale worker result remains diagnostic material and cannot reactivate a descendant.

The new route and orchestration ship behind `MODEL_CHANGE_V0`, disabled by default outside the V0 test/demo environment. Code rollback disables the flag and returns future work to the predecessor release while preserving all V0 records.

Schema reverse is permitted only on an empty pre-population installation. After any V0 canonical record exists, rollback must leave the additive schema dormant and forward-fix. Existing legacy routes and data remain readable. Adapter rollback changes the profile for future episodes and never rewrites a manifest or calculation receipt.
