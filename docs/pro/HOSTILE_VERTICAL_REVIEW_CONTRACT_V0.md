# Hostile Vertical Review Contract V0

Status: active independent-review contract for Milestone 1 of `END_TO_END_DELIVERY_COMMISSION.md`.

The review must determine whether the joined product architecture can support one outcome-complete model-change vertical without collapsing into an Excel automation, a generic research dashboard, an internal harness viewer, or an unimplementable ontology.

The reviewer is an independent expert witness, not a second architectural writer. It may identify defects, contradictions, missing distinctions, excessive objects, migration blockers, false product assumptions and kill conditions. It may recommend exact substitutions. It may not edit governing architecture, product code, prompts or UI.

## Review question

Can the present product system be narrowed into one implementable vertical that:

```text
authenticates and resumes one company job
-> ingests one exact native model artifact
-> recovers and confirms one bounded professional object
-> compiles and runs real NTM/Codex work over exact host-owned evidence
-> blocks one plausible invalid proposal before artifact mutation
-> explains the material exception in ordinary analyst language
-> applies an attributed correction
-> creates and recalculates an exact candidate descendant
-> records a scoped synthetic use, rejection or rework decision
-> survives restart
-> emits an exact correction record suitable for later protected evaluation
```

The review must reject a vertical when frontend and backend can appear successful independently, when the native artifact is simulated, when source identity remains model-authored, when the analyst must reconstruct the whole job, or when migration and rollback are unspecified.

## Independence requirement

The reviewer must start in a fresh context without prior hidden conversation. It receives only the repository, exact base commit and this contract. It must state:

- what it independently inspected;
- what it inherited from governing artifacts;
- what it could not verify;
- whether technical independence from the producing context is established; and
- any source or environment limitation.

Model freshness is not proof of independence. The review may not use model agreement as evidence.

## Case set

### Case A — Existing reported-value update

Use the Micron equal-value/wrong-source counterexample:

- current synthetic target represents consolidated FY2025 GAAP revenue in USD millions;
- both the September 8-K exhibit and October 10-K report `37,378`;
- the configured historical target requires the available 10-K;
- the initial proposal cites the 8-K;
- the host must block before candidate mutation;
- correction to the exact 10-K assertion may later produce a candidate; and
- a separate target must prove that an 8-K, non-GAAP measure, derived value or analyst assumption can be legitimate.

Attack:

- whether source policy is a disguised universal hierarchy;
- whether the analyst is forced to author metadata the product claims to recover;
- whether identical numerical values make the exception feel ceremonial;
- whether the system can show the professional consequence without a provenance console;
- whether the native candidate and recalculation are real; and
- whether scoped use can be tested synthetically without implying professional reliance.

### Case B — Analyst adjustment or assumption

Construct a materially different synthetic case where:

- the artifact target is known;
- the method, not a source document class, is central;
- an analyst-authored assumption or adjustment component has actor, rationale, scope and change condition;
- changing it invalidates downstream candidate state;
- no filing hierarchy can decide professional appropriateness; and
- the product must distinguish reported fact, derived calculation and attributed assumption.

Attack:

- whether the conceptual model has too many visible confirmations;
- whether the method-authority split is usable;
- whether a human assumption can be represented without pretending it is source evidence;
- whether correction and invalidation are exact; and
- whether the same interaction grammar survives without Micron-specific hard-coding.

### Case C — Earnings-derived structural addition

Construct a synthetic event-driven case where:

- a new disclosed segment, line or relationship does not yet have a stable artifact target;
- the system proposes a bounded structural addition;
- economic meaning and method must be confirmed before mutation;
- the adapter must create or safely refuse the new structure;
- dependencies differ from a simple value update; and
- the resulting work remains part of the continuing company job.

Attack:

- whether `ConceptualObjectVersion` can exist before artifact identity without circularity;
- whether the proposed object set handles creation as well as update;
- whether the native adapter is being asked to do unbounded spreadsheet design;
- whether a specialised workspace remains coherent; and
- whether the mature continuing-job frame adds value or merely creates a dashboard shell.

The reviewer must not clone the Micron fixture with renamed cells.

## Repository and migration review

Inspect current models, migrations, services, routes and tests and answer:

1. Which existing objects can be retained without semantic falsification?
2. Which objects are overloaded and require new version or episode semantics?
3. Can the first vertical be implemented additively without destructive migration?
4. Which current route can serve as internal support while a new product route is built?
5. What direct SQL, ORM, tenant and append-only invariants must survive?
6. How does campaign-wide trace finality interact with a continuing job and multiple work episodes?
7. Which objects may be projections rather than canonical tables in V0?
8. What is the smallest migration boundary that supports the complete vertical?
9. What rollback restores the prior repository behaviour without deleting chronology?
10. Which proposed canonical objects are premature and should be represented as immutable JSON contracts until evidence earns dedicated tables?

The review must not equate a complete object catalogue with implementation quality.

## Runtime and cognition review

Inspect the NTM/Codex boundary, active protocols, skill locks, source search policy and collection path.

Determine:

- whether one `bound_work`-derived protocol can support the first vertical;
- how typed proposals can reference host-issued identities;
- whether closed-source work requires disabling `--search` or captured retrieval;
- which runtime identities are needed for a synthetic V0;
- whether job and execution episode can be separated without replacing the runtime;
- whether planning is necessary for the first vertical;
- whether a fresh adversarial worker adds value beyond deterministic tests;
- whether machine judgment should remain outside the product path; and
- which protocol changes are necessary now versus evaluation candidates later.

A prose prompt change cannot be recommended as the repair for a missing source, artifact, transition, permission or validator object.

## Native artifact and adapter review

Compare:

- direct OOXML inspection and patching;
- the historical LibreOfficeDev proxy receipt;
- Excel for the Web as an untested reference surface;
- potential desktop or service calculation routes; and
- safe refusal under unsupported features.

The review must identify the adapter capabilities the first vertical actually requires, rather than requiring generic Excel parity.

It must state whether a real-surface assumption test is required before implementation, can run in parallel, or should be deferred until candidate creation. If required, name the exact decision it changes and recompile scope; do not revive stale Packet 002 automatically.

## Interaction and burden review

For each visible act, state:

- what the analyst sees;
- which canonical fact supports it;
- what action is available;
- what exact state and artifact consequence follows;
- what remains quiet;
- what professional judgment is genuinely required; and
- what review burden is imposed.

Attack these specific risks:

- too many meaning and method confirmations;
- confirmation becoming manual metadata entry;
- ordinary work being interrupted by governance ceremony;
- a rich product collapsing into a thin exception page;
- history becoming a generic activity feed;
- source lineage becoming a provenance console;
- hidden agent work becoming untrustworthy rather than quiet;
- synthetic use mechanics being mistaken for professional permission; and
- cold users needing knowledge of campaigns, work orders, agents, traces or claim ceilings.

## Restart, invalidation and rollback review

The accepted vertical must specify:

- canonical current state after process restart;
- stale packet detection;
- stale conceptual proposal detection;
- descendant invalidation after meaning, method, source or assumption amendment;
- calculation receipt invalidation;
- use-disposition invalidation;
- rollback of code and schema;
- rollback of a promoted experimental harness version; and
- preservation of historical artifacts and decisions.

## Required verdict

Return exactly one primary verdict:

- `ACCEPT_WITH_EXACT_NARROWING`;
- `REVISE_AND_REVIEW_AGAIN`; or
- `KILL_OR_REPLACE_CURRENT_VERTICAL`.

An acceptance must name the smallest outcome-complete vertical and every assumption it narrows. It may not mean that the broader architecture is validated.

A revision verdict must identify the minimum architectural changes and the exact second-review question. It must not create an indefinite document loop.

A kill verdict must name the strongest rival form and the reversible evidence required to test it.

## Prohibited review substitutes

Do not:

- implement code or UI;
- rewrite governing architecture;
- activate dormant prompts;
- add agent roles;
- recommend a generic dashboard or provenance console;
- accept a hard-coded Micron path;
- accept manual attachment of a candidate artifact;
- treat model-authored source metadata as fact;
- require full Excel compatibility;
- call synthetic use professional permission;
- call the product analyst validated; or
- return a generic list of considerations without a verdict and exact vertical boundary.

## Claim ceiling

A successful review can establish only that one outcome-complete vertical is coherent enough to implement within a named migration, adapter, authority and rollback boundary. It cannot establish analyst usefulness, implementation success, spreadsheet compatibility, research quality, professional permission or product fit.
