# UI and Repository Slop Audit

The inherited analyst-facing product is not a rough version of the right interface; it is the wrong product centre rendered with real backend facts.

Status: controlling preserve, demote, replace, and add decisions for the product re-commission. This audit does not authorise deletion or UI implementation.

## 1. Standard used

An object or control earns analyst-facing visibility only when it helps the analyst:

- begin or resume recognisable work;
- understand the system's bounded interpretation;
- supply professional meaning, method, assumption, materiality, or use authority;
- resolve a consequential exception;
- inspect a proposed change and what depends on it;
- obtain or reject a native artifact;
- reconstruct a correction or relied-upon result; or
- reduce future review through a separately governed evaluation loop.

Operational identity, governance ceremony, transport state, backend ontology, model self-description, and decorative grouping do not earn primary visibility.

A backend mechanism earns preservation when it establishes identity, custody, legal transition, safety, reconstructability, evaluation, or rollback. It does not earn product-centre status merely because it is implemented and tested.

## 2. Summary decisions

### Preserve as kernel

- authentication and owner-scoped lookup;
- exact input bytes and digests;
- immutable run specifications;
- proposal disposition before execution;
- canonical work-order compilation;
- version-pinned role, workbench, and skill reads;
- NTM/Codex allowlisted lifecycle;
- tracked dispatch and completion observation;
- sealed output and byte attestation;
- provisional candidate or bounded refusal;
- append-only dispositions and state ancestry;
- restart retrieval;
- post-custody Langfuse correlation; and
- the review product's separation of blind first judgment, reveal, diagnosis, and quarantined future change.

### Demote to support or internal administration

- Campaign Studio and campaign terminology;
- work-order identifiers, packet digests, runtime events, trace IDs, and provider joins;
- readiness, send, collect, correlate, and stop controls;
- detailed source and research-state journals;
- planner, worker, reviewer, synthesis, and judgment role names;
- workbench and reasoning-operator names;
- claim ceilings as a visible product taxonomy;
- raw candidate JSON;
- technical nonclaims as a permanent product panel; and
- the Casebook as an engineering inspection surface.

### Replace

- complex job-creation form with professional intent plus current artifact;
- campaign/job list with company or mandate resumption;
- programme-design controls with conditional work proposals stated by consequence;
- generic approval with distinct meaning, method, work, candidate-use, rejection, and rework actions;
- broad research-state cards with one contextual professional object and material exception;
- raw worker result with native artifact delta and exact support;
- free-text correction with an anchored amendment and corrected descendant;
- campaign-wide finality with continuing job plus immutable episode;
- arbitrary candidate envelope with typed host-reference proposals;
- prompt-authored source receipts with host-captured source versions and assertions; and
- generic future proposal with protected evaluation, promotion, and rollback.

### Add only because the professional job requires it

- bounded system-understanding confirmation;
- conceptual object, method, and authority versions;
- exact source capture, assertions, entitlement, and source policy;
- material exception derived from canonical state;
- candidate native artifact and calculation receipt;
- dependency invalidation and recalculation;
- exact permission to rely for a named use;
- continuing company work with contextual versions and decisions;
- exact correction and failure attribution;
- protected evaluation cases and harness releases; and
- a specialised model-change workspace inside the continuing job.

## 3. `index.html`: complex-SaaS intake disguised as job creation

Current visible fields include:

- job title;
- issuer or security;
- equities decision use;
- evidence cutoff;
- objective;
- `What should Codex produce?`;
- starting artifact;
- sources Codex may use; and
- `Create job without starting work`.

### Judgment

**Replace.** This form asks the analyst to translate their work into the repository's execution contract before the system has understood the professional object. It makes the user author a runtime instruction, decide the complete source population, and comprehend the difference between creating and starting a job.

This is not fixed by better labels, progressive disclosure, fewer borders, or cleaner typography. The causal order is wrong.

### Replacement interaction

The analyst begins with:

- company or mandate;
- what changed or what they are trying to do;
- current model or research artifact;
- named use when known.

The system then proposes the objective, affected conceptual object, cutoff, evidence routes, and bounded work. Missing professional facts are confirmed when material. Runtime instruction is compiled by the product.

### Preserve beneath the interaction

- authenticated ownership;
- exact artifact upload;
- objective and named-use versioning;
- atomic job creation; and
- no automatic execution before authority.

## 4. `job.html`: honest execution receipt mistaken for a product

Current sections expose objective, exact input digests, authorised work, run-specification identity, provisional-result warnings, runtime controls, raw candidate JSON, a permanent `Not established` panel, and an operational record.

### Judgment

**Demote and replace.** This page is honest engineering evidence but not a completed professional workflow.

The controls `Start this work`, `Check readiness`, `Send the exact job`, `Check this work`, and `Collect the exact result` are ceremonial from the analyst's perspective. They correspond to real host transitions, but the analyst has already expressed the only professional authority that matters: run the bounded work. Capacity, dispatch, transport acknowledgement, completion polling, and collection should proceed quietly. A runtime failure should appear only when it changes the analyst's choices or trust.

Printing `{{ bound_outcome.candidate }}` inside `<pre>` is not product transparency. It forces the analyst to interpret an arbitrary backend envelope and still does not show whether the native artifact changed.

The `Not established` section is appropriate in an experimental demo receipt and wrong as a permanent product module. Product truth should be encoded by what actions and claims are legal, not by a standing disclaimer card.

### Preserve beneath the replacement

- exact objective and use;
- exact input versions;
- separate authority before execution;
- provisional-by-default result;
- bounded refusal;
- downloadable exact artifacts;
- operational diagnostics; and
- restart truth.

### Replacement interaction

The model-change workspace should show:

- current professional object and artifact;
- what the system understands;
- current work or material exception;
- proposed change and exact support;
- downstream consequences and calculation state;
- remaining assumptions or ambiguity;
- candidate artifact; and
- exact use, amendment, rejection, or rework action.

Operational record remains support-only.

## 5. `casebook.html`: backend ontology presented as analyst work

The Casebook visibly organises work around:

- `Investment Casebook` eyebrow;
- current investment case;
- research-state cards;
- new evidence receipts;
- working alternatives;
- unresolved uncertainties;
- claim boundary;
- decision consequence;
- proposed next route;
- programme design;
- research decisions;
- approved research;
- campaign runtime;
- evidence in custody;
- operational evidence;
- expert distillation; and
- a technical record.

### Judgment

**Retire as the primary analyst product. Preserve only as an internal state inspector until replaced by better support tooling.**

The page is structurally slop because it exposes almost every implemented object and then asks the user to reconstruct the professional job. The card count creates apparent richness while the core question remains obscure: what exact model, claim, assumption, or artifact is being changed, what requires judgment, and what will the action do?

The terms `research state`, `claim boundary`, `mechanism`, `epistemic delta`, `programme design`, `operational evidence`, and `expert distillation` may be useful internally. They are not validated analyst language and do not become product objects by being rendered clearly.

The page also contains an explicitly forbidden eyebrow. Removing the eyebrow would not repair the product.

### Specific controls judged causally wrong

- `Authorize programme design`: exposes a role/stage instead of a professional consequence.
- `Accept for follow-on research`: confuses permission to continue research with meaning, claim, artifact, or use authority.
- `Challenge and route back`: expresses a state-machine route instead of the exact professional correction.
- `Approve this research step`: too generic; does not say what evidence, artifact, method, cost, or consequence is authorised.
- `Read back operational evidence`: transport diagnostics presented as analyst work.
- `Stop this campaign runtime`: support operation except where a live cost or risk decision requires interruption.
- `Expert distillation`: invented product language for a disconnected review path.

### Useful kernel hidden inside the slop

- explicit distinction between planning permission and research permission;
- candidate state and human disposition;
- accepted-state re-entry;
- rival mechanisms and uncertainty preservation;
- source and state chronology;
- exact runtime and trace receipts; and
- refusal to call machine work analyst judgment.

These should feed specialised professional interactions, not organise the UI.

## 6. Card grids, badges, statuses, and panels

### Judgment

**Reject as default composition.** Cards, badges, status pills, split headers, and grids are not inherently wrong. Here they are used to package backend objects rather than to express professional relationships.

A status such as `awaiting director`, `Planning only`, `accepted for continuation`, or `output in custody` requires the analyst to understand the harness. The product should state the consequence:

- `Confirm what this line represents`;
- `Choose the source for this model line`;
- `The model has not changed`;
- `A recalculated candidate is ready`;
- `This assumption invalidates the previous candidate`; or
- `Use this candidate for the FY2025 historical update`.

Use visual emphasis only to make consequence, uncertainty, or action legible. Do not create a global status system because the backend has enumerations.

## 7. Campaigns, dashboards, and navigation

### Campaign administration

**Demote.** `ResearchCampaign` is a useful current table and an overloaded product concept. It mixes continuing work, one execution population, runtime session, evidence cutoff, and correlation finality.

The product should expose company or mandate work and current objectives. Internal campaign identifiers may remain during migration.

### Dashboard

**Reject by default.** No observed analyst evidence justifies a generic SaaS dashboard of job counts, statuses, activity, agents, or alerts.

A resumption surface may show recent company work and unresolved consequential exceptions. It must be derived from observed work, not installed as a standard enterprise template.

### Sidebar

**Reject by default.** Permanent navigation for Campaigns, Sources, Agents, Evaluations, Settings, and Activity would fossilise backend modules into the product. Specialised views should appear in context when the current professional object requires them.

### Generic activity feed

**Reject.** Time-ordered events are not automatically useful. Present contextual versions, decisions, corrections, and invalidations that answer why the current artifact is in its present state.

## 8. Generic approval and authority collapse

### Judgment

**Replace everywhere.** `Approve`, `Accept`, and `Validated` are dangerous when they do not name the object and scope.

The system must distinguish:

- `CONFIRM_MEANING`;
- `AMEND_MEANING`;
- `AUTHORIZE_METHOD`;
- `RUN_THIS_WORK`;
- `REJECT_PROPOSAL`;
- `REQUEST_REWORK`;
- `USE_CANDIDATE` for one exact named use; and
- `REJECT_CANDIDATE`.

Approval of a plan does not authorise a source. Confirmation of meaning does not authorise a method. A deterministic pass does not authorise use. Use of a candidate does not establish global truth.

Any UI that renders one generic green check for these states is causally false.

## 9. Provenance console and “watch the agents” product story

### Provenance console

**Reject as product centre.** Exact lineage is necessary. A provenance console that asks the analyst to browse source graphs, work-order packets, trace trees, and artifact IDs merely transfers verification labour back to the user.

Lineage should appear where it changes a decision:

- exact source beside the model object;
- method and assumption beside the proposed value;
- affected dependencies beside the candidate;
- correction and invalidation beside the new version;
- use scope beside the final act.

Full graph and receipts remain available for support, audit, and incident investigation.

### Watching agents work

**Reject.** Multi-agent panes, progress animations, role rosters, branch graphs, and visible chain-of-thought are not the value proposition. They create spectacle and often encourage premature trust.

The analyst cares whether the right work was performed, whether a material exception exists, and whether the resulting artifact can be used. Agent topology remains an evaluated implementation choice.

## 10. Separate blind-review product

### Judgment

**Preserve selected mechanisms; replace the disconnected product boundary.** Blind first pass, later lineage reveal, diagnosis, and quarantined future change are valuable. The separate `ResearchCase` product is disconnected from the owned job and exact corrected artifact.

`CurrentCorrection` as free text is ceremonial when it cannot:

- identify the exact source, conceptual object, proposal, or artifact corrected;
- apply a legal amendment;
- invalidate descendants;
- produce a new calculation;
- show the corrected artifact; or
- seed a protected comparison.

The review machinery should become a service over exact job objects and evaluation cases. It should not remain a parallel product ontology.

## 11. Prompt and protocol slop

### Worker-authored source receipts

**Self-certifying and unacceptable as authority.** Rich receipt fields in a prompt do not make source identity machine-owned. Preserve them as model interpretation only after host-issued source versions and assertions exist.

### Arbitrary non-empty candidate JSON

**Premature flexibility that destroys product semantics.** The bound candidate envelope is appropriate for a generic custody spike and wrong for a professional product. Replace with typed operations over host-issued identities.

### Mandatory reasoning operator

**Ceremonial.** Requiring one reasoning operator for every research-worker proposal rewards invented failure tests. Permit zero. Require one only when a named defect and expected delta justify it.

### Automatic Research Frame selection

**Evaluate, do not universalise.** It may improve ambiguous programme compilation and is unnecessary for an exact lookup or direct model update. Invocation must earn a changed branch, discriminator, stop, refusal, or claim boundary.

### Dormant DeepResearch suite

**Premature as a bundle.** It contains useful candidate semantics and also narrates host gaps. Do not activate it wholesale. Test individual protocol candidates after the host objects and evaluation runner exist.

### One role per conceptual stage

**Potential topology slop.** Planner, worker, reviewer, synthesis, and judgment should remain semantic protocols. A separate model context is justified only by evidence, permissions, independence, or context economy.

### Synthesis as mandatory completion

**Reject.** Some jobs complete with a corrected model artifact, bounded calculation, source comparison, or refusal. A prose synthesis is conditional, not the universal endpoint.

### Machine judgment in the product path

**Demote to evaluation sidecar.** It is not analyst authorship and does not need a visible product stage.

## 12. Repository and lifecycle slop

### Campaign-wide correlation finality

**Replace.** Final trace correlation for one execution population should not freeze an ongoing job. Introduce immutable episode finality inside a continuing job or block later work deterministically.

### Filesystem outputs as professional state

**Demote.** `branch.md`, `plan.md`, `review.md`, `synthesis.md`, JSON state, and attestations are useful worker artifacts. They should not become the primary professional object when the actual product output is a workbook, model change, source decision, assumption, or research conclusion.

### Research-state schema as universal memory

**Reject as universal product ontology.** Append-only state and epistemic delta are useful for research continuation. They do not represent every artifact, method, authority, source entitlement, correction, or use relation needed by the product.

### Institutional memory as an early feature

**Premature.** Durable history is necessary. “Institutional memory” becomes meaningful only after exact professional objects, corrections, use decisions, and reusable evaluations accumulate. Building a generic memory layer now would preserve unvalidated abstractions and model-authored metadata.

### Prompt rewrite before host seam

**Causally wrong.** The prompt audit already states the distinctions. Better prose cannot make source identity, target meaning, artifact operations, calculation, or use authority host-owned.

### Agent proliferation after a semantic failure

**Slop.** Adding a provenance critic, spreadsheet critic, or consensus panel does not remove self-certification when every agent reads the same model-authored metadata and no host fact exists.

### Agentic SDLC wholesale adoption

**Reject.** Its durable artifacts, run records, reconstitution, writer ownership, and deterministic-versus-judgment distinction are useful. Its software stage taxonomy, filesystem authority, overwrite model, and review fan-out are not the analyst product.

## 14. What not to build next

Do not build:

- a styled replacement for the Casebook;
- a dashboard shell around existing campaign state;
- an Excel pane that only displays provenance;
- a wizard mapping every backend field to a form;
- a multi-agent monitor;
- a source graph explorer as the main workflow;
- a settings area for prompts, skills, agents, and policies;
- a generic exception inbox before contextual exceptions are observed at scale;
- an institutional memory page;
- a universal conceptual ontology;
- a broad prompt rewrite;
- another worker role; or
- a backend model package without the exact analyst interaction and artifact consequence it supports.

## 15. What the next implementation must prove

When implementation is later authorised, the first vertical must join frontend and backend in one falsifiable path:

```text
state the model change
-> inspect exact artifact
-> propose bounded understanding
-> confirm or correct meaning
-> capture exact source facts
-> run one bounded agent job
-> block one wrong proposal before mutation
-> explain the exception in ordinary analyst language
-> apply an attributed correction
-> calculate a candidate artifact
-> show exact consequences
-> permit or reject use for one named purpose
-> resume the same state after restart
```

A backend-only completion, polished mock-up, static fixture, raw JSON, or manually attached workbook fails the product contract.

## 16. Current decision

The existing build sequence changes. Product implementation remains premature. The direct Excel assumption test and queued classifier repair may continue as bounded adapter and repository investigations, but neither authorises a UI or backend slice.

Before implementation, a hostile review must challenge the joined architecture and interaction contract against:

- the Micron existing-model update;
- one model adjustment or assumption change;
- one earnings-derived or structural addition;
- the exact current repository migration surface; and
- the analyst burden implied by confirming meaning and method.

No new implementation worker packet is issued by this audit.
