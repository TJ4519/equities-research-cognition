# Master plan

Status: first integrated plan. The project remains in plan space.

Method source: Jeffrey Emanuel’s Agentic Coding Flywheel guide, adapted rather than copied. The useful principles are front-loaded whole-system reasoning, competing plans, fresh-context revision, an explicit transition from plan to dependency-aware work, durable instructions that survive compaction, vendor-neutral agents, and a feedback loop that changes reusable tools only after observed use.

The software-development vocabulary in that guide does not define analyst work.

## 1. The planning posture

The project should spend its present effort on the representations that still fit in one model context:

- professional request;
- product claim;
- conceptual objects;
- source and authority relations;
- local and hosted boundary;
- context construction;
- skills;
- runtime adapters;
- artifact actions;
- inference-state replay;
- evaluation;
- first commercial use; and
- migration from the existing repository.

The project should not convert the plan into implementation work while fresh review still changes those matters substantially.

The current repository shows the cost of deciding too early. A narrow source check became a product centre. NTM runtime repair consumed attention because the runtime had acquired architectural importance. The new plan should make those choices replaceable before more code surrounds them.

## 3. The product proposition to test

The working proposition is:

> A sophisticated analyst can use a configured local workspace through an approved terminal agent to state broad professional work, recover exact prior context, invoke supported research and artifact methods, correct results, and resume later. A local service makes consequential sources, contexts, derivations, artifact changes, permissions, and replay reconstructible. An optional shared service adds team functions only after individual usefulness is established.

The proposition includes several separate claims:

1. Terminal-native work reduces adoption friction for analysts already using capable agents.
2. Structured intent interpretation can preserve broad requests without forcing the analyst to design an agent workflow.
3. Exact context construction can keep evidence use inspectable and enforce exclusions.
4. Skills can make research methods repeatable without becoming the authority layer.
5. Native artifact actions can carry useful results into the analyst’s existing work.
6. Inference-state replay can explain and re-derive consequential outputs more usefully than transcript inspection.
7. Corrections can improve later work without polluting memory or changing methods prematurely.
8. The controls can reduce review effort rather than add another compliance burden.

Each claim needs separate evidence. A passing source gate does not prove the proposition.

## 4. First user and first commercial form

The first user should be one sophisticated analyst or a small team already experimenting with Claude Code, Codex, or another capable terminal agent.

The first commercial form should be a productised installation and service:

```text
workspace installation
-> approved local sources and artifacts
-> client-specific methods and skills
-> historical episode reconstruction
-> measured live use
-> correction and replay
-> method improvement
-> analyst training
```

The consulting company should record every human intervention. A useful delivered result may depend upon consultant skill rather than software. The distinction decides whether the work can become a product business.

The first offer should not promise a universal research platform, autonomous investment decisions, or enterprise institutional memory.

## 5. The first proof

The first proof should contain two linked historical episodes and one useful native output.

### Episode one

Episode one begins with:

- an exact prior note, model, or other artifact;
- a broad professional request;
- public or lawfully supplied source material;
- one source whose permitted use differs by purpose;
- one matter of professional meaning the model may misunderstand;
- one research method;
- one challenge;
- one useful artifact or durable note;
- one analyst correction; and
- one scoped use decision.

The Micron equal-value source route should appear as one protected relation inside the episode.

The analyst-facing result should answer what changed, why it matters to prior work, what the system produced, and what still needs judgment.

### Episode two

Episode two begins from the corrected perspective.

The system should:

- retrieve the earlier correction within its scope;
- avoid broadening the correction;
- apply the source-use rule correctly;
- compare new evidence with prior work;
- produce another useful result;
- show lower or equal review burden; and
- support inference-state replay.

### Proof conditions

The proof succeeds only when:

- the analyst uses at least one output;
- the analyst does not reconstruct most of the result;
- the unsafe evidential route remains blocked without blocking legitimate uses of the same source;
- the current correction does not require restarting the whole episode;
- the second episode begins from the corrected state;
- no consultant repair is hidden;
- the exact contexts and derivations can be inspected;
- the result can be reproduced or independently re-derived at the declared replay grade; and
- the total work meets a stated time or coverage threshold.

The proof fails when the result is a competent generic report, a static audit display, or a synthetic workbook demonstration disconnected from repeated analyst work.

## 6. Planning rounds

The plan should pass through fresh independent reviews before work translation.

### Round A: product and professional work

Ask a fresh strong model to attack:

- the first buyer;
- the reason to return;
- the terminal-native choice;
- the difference from generic deep research;
- the value of native artifact work;
- the commercial threshold;
- the service-to-product path; and
- the danger that the consultancy is selling manual research under a software story.

The reviewer should propose a rival product, not merely criticise this one.

### Round B: AI engineering

Ask a fresh strong model to attack:

- intent interpretation;
- context economy;
- agent decomposition;
- terminal-session persistence;
- runtime portability;
- tool and skill boundaries;
- Pydantic boundary use;
- exact context exclusion;
- model-written source receipts;
- replay of stochastic outputs; and
- evaluation design.

### Round C: data, security, and rights

Ask a fresh strong model to attack:

- local encryption;
- key ownership;
- source retention;
- broker and expert-network licensing;
- connector identity;
- client separation;
- process sandboxing;
- terminal-agent access;
- trace redaction;
- synchronisation; and
- revocation.

### Round D: native artifacts

Ask a fresh strong model to compare:

- cited research note;
- reproducible statistical analysis;
- chart;
- mini-model;
- workbook inspection;
- workbook mutation; and
- native-tool companion.

The review should recommend the smallest artifact action that proves useful work without allowing Excel engineering to dominate the product.

### Round E: architecture path

Ask independent reviewers to compare:

1. extend the Django application;
2. build a local kernel beside it; and
3. build the local kernel cleanly while retaining Django as prior art or a later shared service.

The comparison should use exact repository evidence.

### Round F: synthesis

One fresh synthesis model should integrate the strongest revisions. Another implementation-minded model should review the integrated plan and state which changes it accepts, questions, or rejects.

The plan should preserve disagreement where no evidence settles it.

## 7. Convergence

Planning should stop when several fresh reviews satisfy all of these conditions:

- revisions are small and mostly corrective;
- the same product claim survives;
- no new durable object is required by a common professional episode;
- the first proof remains coherent;
- the local and hosted boundary remains stable;
- the architecture path has a reasoned winner;
- major security and rights questions have planned answers;
- every first-release capability has a verification route;
- counterfactuals no longer reveal a different product; and
- remaining disputes concern execution order, test obligations, or local interface detail.

Shorter reviews do not necessarily prove convergence. A tired context may simply stop finding problems. Fresh sessions and explicit comparison with the previous revision are required.

The plan should record a change log across review rounds. The log should state what changed, what evidence caused the change, and which earlier claim was retired.

## 8. Transition to dependency-aware work

The project should create a work graph only after convergence.

Every material plan element should map to at least one work item. Every work item should point back to the plan statement it implements or tests.

The graph should distinguish:

- product experiments;
- technical research;
- architecture decisions;
- implementation;
- hostile tests;
- historical episode reconstruction;
- live use;
- replay and evaluation; and
- commercial measurement.

A work item should contain:

- objective;
- reason;
- exact plan references;
- dependencies;
- owned files or components;
- expected user-visible effect;
- tests;
- evidence required;
- nonclaims;
- stop conditions; and
- review boundary.

The project should not use “packet” as the default unit. The durable unit is a dependency-aware piece of work. The chosen task tool may later store it as a bead.

The graph should be reviewed in both directions:

- plan to work: no material plan element is missing;
- work to plan: no item exists merely because the codebase makes it convenient.

## 9. Proposed implementation phases

The phases below express dependency, not a promise of sequence. Planning review may change them.

### Phase 0: repository and package decision

Decide where the local kernel lives.

Required work:

- compare the three architecture paths;
- identify reusable Django modules and tests;
- identify campaign-shaped assumptions to avoid;
- define package boundaries;
- define migration and coexistence policy;
- select the first supported operating systems;
- select the local database and object-store approach; and
- revise project instructions.

Exit evidence:

- architecture decision with exact repository references;
- local installation story;
- data ownership story;
- package map;
- test strategy; and
- rollback if the selected path proves wrong.

### Phase 1: local workspace kernel

Build the smallest local authority independent of model quality.

Required capability:

- workspace initialisation;
- local database and migrations;
- content-addressed objects;
- stable identifiers;
- append-only history for consequential objects;
- actors and local mandate;
- episodes and perspective versions;
- CLI status and inspection;
- atomic writes;
- backup and recovery;
- safe deletion and retention states; and
- hostile storage tests.

The phase should not implement broad agent orchestration.

Exit evidence:

- a workspace survives restart;
- exact object versions remain retrievable;
- corrupted or substituted bytes are rejected;
- stale writes fail;
- an export can reconstruct public-safe state; and
- private bytes remain excluded from Git.

### Phase 2: source, assertion, and context authority

Required capability:

- local file capture;
- one public web capture route where lawful;
- source identity and time;
- assertion proposal and host issuance;
- entitlement and retention fields;
- professional-object proposal;
- evidence-use decisions;
- context build and materialisation;
- excluded-item records;
- manifest hashing;
- read-only context inspection; and
- tests proving excluded evidence does not reach a child process.

The phase should include the Micron equal-value case and at least one legitimate earnings-release use.

Exit evidence:

- source and assertion identity survive equal values;
- evidence use differs by purpose;
- the model cannot cite an unissued source as authoritative;
- exact context population can be reconstructed; and
- a strict rule does not block the legitimate comparison case.

### Phase 3: terminal research lead and direct runtime

Required capability:

- one vendor-neutral CLI or MCP interface;
- `research-start` and `research-resume` skills;
- proposed and confirmed commission;
- direct child-process adapter;
- exact working directory and process identity;
- stdout, stderr, exit state, and output custody;
- context-bound run;
- checkpoint and restart;
- optional Langfuse link; and
- refusal when a requested action is unsupported.

NTM may be tested as an optional operator surface. It should not block the phase.

Exit evidence:

- Claude Code or Codex can be replaced without changing canonical objects;
- a fresh session resumes one episode without conversational relay;
- completion requires exact process and output evidence;
- the terminal lead cannot bypass the context builder; and
- Langfuse loss does not destroy professional state.

### Phase 4: first research method

The first method should solve useful research rather than merely exercise schemas.

Leading candidate:

```text
purpose-bound evidence comparison
-> compare new earnings material with one exact prior note or thesis view
-> preserve contradictions
-> return a typed change account and cited rendered note
```

Required capability:

- broad discovery under the mandate;
- exact source capture;
- purpose-specific support context;
- typed claim set;
- one independent challenge;
- cited rendering;
- unsupported-claim check;
- unresolved-question preservation; and
- analyst amendment.

Exit evidence:

- the result identifies what changed against prior work;
- citations resolve to exact assertions;
- the challenge can change or narrow the claim set;
- a correction produces a new result without rewriting history; and
- review time is measured.

### Phase 5: first useful artifact action

The plan review must choose one artifact action.

Candidate A: reproducible statistical analysis.

Candidate B: chart with exact data and method lineage.

Candidate C: bounded workbook inspection and candidate change.

Candidate D: amendment to a prior research note.

The choice should follow the first analyst’s repeated work and the shortest route to a used artifact.

Required capability:

- exact parent artifact;
- structural inspection;
- professional-object binding where needed;
- proposed operation;
- admitted inputs;
- deterministic tool receipt;
- candidate descendant;
- diff;
- open in native tool; and
- scoped use decision.

Exit evidence:

- the analyst uses the artifact;
- the original remains intact;
- the operation can be replayed at the declared grade;
- unsupported features are visible; and
- artifact use does not promote the method.

### Phase 6: correction, active memory, and second episode

Required capability:

- attributed correction;
- dependent-object identification;
- current-result amendment;
- active-memory proposal;
- scoped memory decision;
- second perspective version;
- second historical episode;
- retrieval of the earlier correction; and
- detection of over-broad memory use.

Exit evidence:

- episode two uses the correction within scope;
- unrelated work does not inherit it;
- the analyst can see what entered active memory;
- archive and active memory remain separate; and
- review burden does not increase.

### Phase 7: inference-state replay

Required capability:

- backward explanation from claim or artifact;
- source replay;
- context replay;
- deterministic derivation replay where applicable;
- independent evidential re-derivation;
- authority replay;
- proof-pack export;
- baseline comparison; and
- one counterfactual intervention.

Exit evidence:

- the Micron relation can be re-derived;
- the useful result from episode one can be independently supported;
- the system states its replay grade honestly;
- changing one rule changes only expected objects; and
- later evidence cannot leak into a historical replay.

### Phase 8: evaluation and method release

Required capability:

- evaluation-case registry;
- baseline and candidate workspace versions;
- protected and held-out cases;
- measures for unsafe admission, false blocks, useful claims, review time, cost, and artifact use;
- shadow method state;
- promotion decision;
- scope and expiry;
- rollback; and
- later harm or override monitoring.

Exit evidence:

- one correction becomes a candidate rather than a rule;
- several varied cases justify or reject broader use;
- a promoted change has a narrow scope;
- rollback is tested; and
- the live workspace never updates itself from an unreviewed click.

### Phase 9: optional shared service

The phase should begin only after repeated local use.

Possible capability:

- team identity;
- connector credentials;
- source entitlements;
- shared methods;
- synchronisation;
- schedules;
- monitoring;
- evaluation runners;
- method release channels;
- administrative audit; and
- usage controls.

Exit evidence:

- local work remains possible;
- synchronisation preserves immutable history;
- conflicts remain explicit;
- cross-mandate retrieval fails closed;
- team policy and analyst authority can disagree without silent overwrite; and
- the shared service reduces work rather than adding clerical administration.

## 10. Technical research before stack lock

The plan needs current primary-source research on:

- terminal-agent CLI and MCP capabilities;
- direct Codex and Claude Code process contracts;
- supported ephemeral and non-interactive modes;
- local MCP server libraries;
- SQLite encryption and backup options;
- operating-system key stores;
- process sandboxing on macOS, Linux, and Windows;
- local hybrid search;
- content-addressed storage patterns;
- Langfuse SDK and data-residency options;
- Office Open XML inspection and calculation engines;

The research should distinguish official support from convenient experiments.

No plan should assume that a terminal agent subscription may be multiplexed commercially across users.

## 11. Evaluation families

The protected body of cases should grow from several families.

### Evidence and time

- equal values from different sources;
- different values from different sources;
- preliminary source before filing;
- filing amendment;
- inaccessible source;
- transient licensed source; and
- historical cutoff replay.

### Professional meaning

- correct cell, wrong metric;
- correct metric, wrong scope;
- copied workbook with changed meaning;
- management statement with changed definition;
- estimate presented as fact; and
- assumption broadened beyond its scenario.

### Derivation

- derived value;
- statistical result;
- chart transformation;
- workbook calculation;
- unsupported formula;
- stale cached value; and
- conflicting calculation engines.

### Research quality

- useful contradiction preserved;
- generic report disconnected from prior work;
- unsupported addition;
- missing important claim;
- overconfident synthesis;
- legitimate uncertainty; and
- refusal that should have become a question.

### Memory

- correction remembered correctly;
- correction forgotten;
- correction broadened;
- expired assumption reused;
- abandoned scenario retrieved;
- artifact use mistaken for claim acceptance; and
- model summary promoted without authority.

### Commercial use

- output used without reconstruction;
- output useful only after consultant repair;
- review burden too high;
- source controls block routine work;
- repeat use on a later event; and
- coverage increase at fixed analyst time.

## 12. Measures

Every historical or live episode should record:

- analyst minutes;
- consultant minutes;
- elapsed time;
- model and infrastructure cost;
- context size;
- sources inspected;
- assertions admitted, quarantined, and rejected;
- unsafe routes proposed;
- unsafe routes admitted;
- legitimate routes blocked;
- claims produced;
- claims corrected;
- artifacts produced;
- artifacts used;
- amount rebuilt manually;
- interruptions;
- memory entries proposed and accepted;
- repeat use; and
- replay grade.

The first commercial threshold remains provisional:

- at least 50 percent less analyst time for the same scope; or
- at least twice the useful coverage for the same analyst review hours.

## 13. Instructions for later coding agents

Later agents should receive project instructions that say, in ordinary language:

- The analyst’s broad request is not the child process contract.
- Canonical state lives in the local service, not in terminal memory.
- Skills teach procedures but cannot create authority.
- Source assertions remain distinct despite equal text or numbers.
- Evidence use is purpose-specific.
- Child context comes only from a sealed context build.
- Model outputs are proposals.
- Native artifacts produce descendants.
- Human correction does not rewrite history.
- Artifact use, memory, and method release are separate decisions.
- Runtime sessions are replaceable.
- Langfuse is diagnostic.
- Replay must be possible from durable objects.
- No interface should expose backend nouns as analyst work.
- No completion claim may exceed the exact tests and episodes run.

The instructions should be revised after plan convergence and after each observed class of agent confusion.

## 14. Feedback into reusable infrastructure

The Flywheel compounds only when observed use changes reusable artifacts.

For this product, the loop should read:

```text
real episode
-> exact session and professional state
-> analyst correction or measured friction
-> diagnosis of the responsible layer
-> candidate change to skill, prompt, method, tool, context, or software check
-> counterfactual replay
-> protected and held-out comparison
-> scoped promotion or rejection
-> later monitoring
```

Raw session repetition may suggest a useful procedure. Repetition alone should not authorise a professional method.

A repeated terminal prompt may become a skill after several successful uses.

A repeated identity or arithmetic check should become software.

A repeated analyst judgment may become a proposed question, template, or policy only after its class and scope are understood.
